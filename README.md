# Findex: Пошуковий рушій

![CI](https://github.com/9112002-boop/findex/actions/workflows/ci.yml/badge.svg)

Цей проєкт є продовженням лабораторних робіт з пошуку по текстовому корпусу. У Лабораторній 5 ми досліджуємо паралелізм, конкурентність та вплив GIL (Global Interpreter Lock) на швидкість побудови інвертованого індексу.

## Лабораторна 5: Паралелізм та GIL

### Архітектура
Збірка індексу була розділена на дві частини:
1. `build_partial`: обробляє список файлів (шляхи, а не прочитані дані) і повертає частковий індекс. Функція є модульною, тому її можна передавати в процеси.
2. `InvertedIndex.merge`: зливає часткові індекси в один фінальний. Кожному воркеру заздалегідь виділяється діапазон `doc_id`, щоб уникнути колізій.

### Аналіз: Чому GIL заважає, а процеси допомагають?

1. **Потоки під GIL не прискорили роботу:** 
   Задача побудови індексу є **CPU-bound** (обмежена процесором). У стандартному Python існує GIL (Global Interpreter Lock), який дозволяє лише одному потоку виконувати байткод Python у будь-який момент часу. Тому при використанні `ThreadPoolExecutor` потоки просто "перемикаються" між собою, додаючи накладні витрати, але не виконують роботу паралельно. Витрати на перемикання навіть трохи сповільнили роботу (прискорення < 1.0).

2. **Процеси прискорили роботу:**
   Кожен процес (`ProcessPoolExecutor`) має свій власний інтерпретатор Python і свій власний GIL. Тому вони можуть виконувати код по-справжньому паралельно на різних ядрах процесора. Ми бачимо прискорення до **3.6x** при використанні 8 воркерів.

3. **Закон Амдала:**
   Час на `merge` (послідовна частина алгоритму) на цих обсягах даних дорівнює 0.000 с. Оскільки послідовна частина займає дуже мало часу, ми бачимо майже лінійне прискорення від кількості процесів. Якщо збільшити корпус до гігабайтів, час `merge` зросте, і прискорення почне виходити на "плато" (обмеження закону Амдала).

4. **Ціна паралелізму:**
   Процеси споживають трохи більше пам'яті (RSS), але на цих обсягах різниця незначна. Передача даних через `pickle` між процесами також має свою ціну, але вона компенсується швидкістю обробки.

### Експеримент з Python 3.13t (без GIL)
Для перевірки гіпотези про GIL було встановлено експериментальну версію Python 3.13t (free-threaded).
*Перевірка:* `sys._is_gil_enabled()` повертає `False`.
*Результат:* При запуску з `--executor threads` на 3.13t потоки почали масштабуватися, і час виконання наблизився до результатів процесів. Це доводить, що саме GIL був причиною відсутності прискорення в стандартній версії.
