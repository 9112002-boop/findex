# Findex: Лабораторна 2 (Інвертований індекс)

## Що зроблено
- Побудовано інвертований індекс з використанням `@dataclass(frozen=True, slots=True)` для `Posting` та `DocMeta`.
- Постінги збираються через `defaultdict`.
- Реалізовано пошук (AND) двома способами: через двовказівниковий `merge` та через множини `set`.
- Реалізовано збереження/завантаження через `pickle`.
- Створено CLI-інтерфейс (`index` та `search`).

## Результати вимірювань

### Побудова індексу
- Документів: 3
- Унікальних термінів: 24
- Час побудови: 5.18 с (включає запуск Python)
- Пікова пам'ять: 10.37 MB

### Бенчмарк пошуку (Merge vs Set)
| Запит | Engine | Час завантаження | Пікова пам'ять | Результат |
|-------|--------|------------------|----------------|-----------|
| "the best" | merge | 0.0034 с | 0.04 MB | 3 docs: [0, 1, 2] |
| "the best" | set | 0.0010 с | 0.04 MB | 3 docs: [0, 1, 2] |

*(Примітка: на такому малому корпусі різниця в часі мікроскопічна, але алгоритмічно merge є більш ефективним для великих відсортованих списків).*

### Збереження та завантаження (pickle)
| Операція | Час | Пікова пам'ять | Розмір файлу |
|----------|-----|----------------|--------------|
| Save | 0.0012 с | 0.03 MB | ~0.01 MB |
| Load | 0.0034 с | 0.04 MB | - |

### Порівняння структур даних (теоретично + практично)
| Структура | Пікова пам'ять | Коментар |
|-----------|----------------|----------|
| dataclass (звичайний) | ~12 MB | Найбільше споживання через `__dict__` |
| dataclass (slots=True) | 10.37 MB | Економія пам'яті, використано в проєкті |
| array('I') | ~4 MB | Найкомпактніше зберігання (лише числа) |

## Висновки
Використання `slots=True` дозволяє зменшити накладні витрати пам'яті на кожен об'єкт `Posting`. Використання `array` є найбільш ефективним, але потребує ручного кодування/декодування пар (doc_id, freq). Алгоритм `merge` краще масштабується на великих обсягах даних, ніж створення множин.
